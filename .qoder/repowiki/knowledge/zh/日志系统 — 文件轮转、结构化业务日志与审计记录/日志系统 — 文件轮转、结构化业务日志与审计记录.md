## 1. 使用的框架与工具
- 输出层：基于 Gin 的 `gin.DefaultWriter` / `gin.DefaultErrorWriter`，通过 `io.MultiWriter` 同时写入 stdout/stderr 和文件。
- 日志库：未引入第三方日志框架，使用自实现的 `logger` 包 + Gin 内置 logger 中间件。
- 持久化存储：业务/审计日志通过 GORM 写入独立数据库（支持 MySQL/PostgreSQL/SQLite/ClickHouse），由 `model/log.go` 统一管理。
- 异步与并发：使用 `github.com/bytedance/gopool` 的 `gopool.Go` 进行后台任务调度（如日志文件轮转）。

## 2. 核心文件与职责
- `logger/logger.go`：应用级日志门面，提供 INFO/WARN/ERR/DEBUG 四级输出、按请求 ID 关联、自动文件轮转、配额格式化等能力。
- `middleware/logger.go`：Gin HTTP 访问日志中间件，统一输出 `[GIN] ...` 格式，包含 tag、request_id、状态码、耗时、客户端 IP、方法与路径。
- `common/sys_log.go`：系统级日志辅助函数（SysLog/SysError/FatalLog/LogStartupSuccess），用于启动、关闭、异常等关键事件。
- `model/log.go`：业务与审计日志的数据模型与持久化逻辑，定义 Log 结构体、类型枚举、CRUD、统计查询、旧日志清理等。
- `main.go`：初始化顺序中调用 `logger.SetupLogger()` 与 `middleware.SetUpLogger(server)`，完成日志子系统装配。

## 3. 架构与约定
### 3.1 应用日志（stdout/stderr + 文件）
- 级别与常量：`INFO`、`WARN`、`ERR`、`DEBUG` 四个级别，分别对应 `LogInfo`、`LogWarn`、`LogError`、`LogDebug`。
- 上下文关联：通过 `common.RequestIdKey` 从 gin.Context 提取 request_id，所有日志行均携带该标识，便于跨服务链路追踪。
- 输出格式：`[LEVEL] 时间 | request_id | 消息`，INFO 走 DefaultWriter，其他级别走 DefaultErrorWriter。
- Debug 开关：仅当环境变量 `DEBUG=true` 时才会输出 DEBUG 级别与 `LogJson` 调试输出。
- 文件轮转：当累计写入超过 `maxLogCount=1000000` 条后，后台 goroutine 触发 `SetupLogger()` 重新打开新文件，文件名带时间戳 `oneapi-YYYYMMDDHHmmss.log`；旧文件句柄安全关闭。
- 线程安全：通过 `common.LogWriterMu`（RWMutex）保护对 Gin writer 的读写，避免轮转期间的竞态。

### 3.2 HTTP 访问日志
- 中间件 `SetUpLogger` 注册为 Gin 全局中间件，使用自定义 `LogFormatterParams` 格式化输出。
- 字段包括：时间戳、路由标签（默认 `web`）、request_id、HTTP 状态码、延迟、客户端 IP、方法、路径。
- 路由标签通过 `RouteTag(tag)` 中间件设置，便于区分不同子系统的访问日志。

### 3.3 系统日志
- `SysLog`/`SysError`/`FatalLog` 直接写 Gin writer，格式为 `[SYS]/[FATAL] 时间 | 消息`。
- `LogStartupSuccess` 在启动成功后打印彩色欢迎信息，包含本地/网络地址、启动耗时、安全警告等。

### 3.4 业务与审计日志（持久化）
- 数据模型 `Log` 包含用户、时间、类型、内容、用户名、token、模型、额度、tokens、耗时、是否流式、渠道、IP、request_id、上游 request_id、扩展字段等。
- 日志类型枚举：`Unknown(0)`、`Topup(1)`、`Consume(2)`、`Manage(3)`、`System(4)`、`Error(5)`、`Refund(6)`、`Login(7)`。
- 写入入口：
  - `RecordLog`：通用操作日志。
  - `RecordLoginLog`：登录审计，包含 action+params 供前端 i18n 渲染。
  - `RecordOperationAuditLog`：管理/高危操作审计，分离 `admin_info` 与 `audit_info` 字段。
  - `RecordTopupLog`：充值审计，附带服务器节点、版本、支付方式等信息。
  - `RecordErrorLog`：错误日志，可配置是否记录 IP。
  - `RecordConsumeLog`：消费日志，记录 prompt/completion tokens、quota、channel、group 等，并可选导出到 quota 数据表。
  - `RecordTaskBillingLog`：任务计费日志，支持多节点场景。
- 查询接口：`GetAllLogs`、`GetUserLogs`、`SumUsedQuota`、`SumUsedToken` 等，支持按类型、时间、模型、用户名、token、渠道、分组、request_id、上游 request_id 过滤。
- ClickHouse 适配：当使用 ClickHouse 作为日志库时，采用专用排序、批量删除（ALTER TABLE DELETE）与显示 ID 分配逻辑。
- 旧日志清理：`DeleteOldLogBatch` 按时间阈值分批删除，ClickHouse 下一次性执行 ALTER TABLE DELETE。

## 4. 约定与约束
- **日志级别使用约定**：INFO 用于正常业务流程跟踪，WARN 用于可恢复异常或降级，ERR 用于失败与错误堆栈，DEBUG 仅在 DEBUG=true 时输出详细调试信息。
- **RequestID 贯穿**：所有日志必须通过 gin.Context 传递 request_id，确保请求链路可追踪。
- **敏感信息脱敏**：业务日志中的 content 字段通过 `common.LocalLogPreview` 进行预览裁剪，避免泄露敏感数据。
- **IP 记录可配置**：是否记录客户端 IP 由用户设置 `RecordIpLog` 控制，默认不记录。
- **消费日志开关**：`common.LogConsumeEnabled` 控制是否记录消费日志，关闭时可跳过高开销写入。
- **数据导出开关**：`common.DataExportEnabled` 控制是否将消费日志同步导出到 quota 数据表，影响性能与存储。
- **文件轮转阈值**：固定 100 万条触发一次轮转，避免频繁 IO 开销。
- **Gin 中间件链顺序**：RequestId → Version → I18n → Logger，确保访问日志能获取到 request_id 与语言上下文。
- **多数据库支持**：日志库与业务库分离，通过 `LOG_DB` 连接，支持 MySQL/PostgreSQL/SQLite/ClickHouse，查询逻辑根据数据库类型动态调整。
